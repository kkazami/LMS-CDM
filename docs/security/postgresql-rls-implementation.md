# PostgreSQL defense and isolated RLS implementation

Sprint 4 implements a disposable `pilot.course` read policy. The fixture models institutes, assigned instructors and approved student enrollment. A restricted runtime principal receives course SELECT and policy-function EXECUTE. It receives no object ownership, grant administration, bypass flag, write privilege or enrollment table permission. The function fixes its search path and qualifies the referenced enrollment relation. Context-free reads produce no rows. The fixture demonstrates transaction reset, role decisions and schema/data recovery. [Policy fixture](../../tests/sprint-4/rls-pilot.sql) · [Policy checks](../../tests/sprint-4/rls-checks.sql)

The application must derive identity, role and institute from trusted session admission before provisioning every transaction. A Prisma pilot should use parameterized `set_config` calls with `is_local = true` inside the same interactive transaction as the protected operations. Every ORM query must use that transaction client. The database role can set custom variables, so RLS under a shared principal protects against missing application predicates and has limited strength under full runtime compromise. Production Prisma/Neon pooling, query plans, maintenance and write policies need independent staging evidence.

| Data family | Design target |
|---|---|
| Institute/course roots | Use explicit instituted actor context and course ownership first. Index the institute relation and review administrative cross-course workflows. |
| Enrollment, assessments, submissions, gradebook | Derive access through persisted course and student relationships. Retain approved enrollment, field-level grades, instructor rules and authoritative grading in application services. Add operation-specific `USING` and `WITH CHECK` with bounded query plans before rollout. |
| User-owned preferences and content | Bind user ID and institute. Evaluate legitimate public/shared or delegated access individually. |
| Identity, sessions, MFA/credentials, global integrations | Keep protected functions and separate login/bootstrap workflows. Plan these independently because authentication precedes admitted tenant context. Keep provider, global maintenance and administrative exceptional workflows explicit. |

Separate runtime, migration owner, narrowly scoped operator and backup/recovery principal. Review effective inherited grants, default privileges, function EXECUTE, schema writes, ownership and any bypass capabilities. Runtime is never a schema owner or backup principal. Rehearse an ordinary read-only cohort first, then writes and selected tenant-owned records by reviewed migration group. Keep a revert SQL proposal per policy group. Rollback retains the server authorization controls. Any production-wide RLS rollout requires explicit approval, full staging and recoverable grant/policy receipts.
