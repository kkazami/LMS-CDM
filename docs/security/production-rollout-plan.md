# Controlled production rollout plan

The release owner authorizes each stage against an immutable commit, build ID, lockfile and evidence receipt. Keep the current candidate local. The [release assessment](final-release-readiness-assessment.md) lists blocking evidence. [Rollback plan](production-rollback-plan.md)

| Stage | Required before approval | Acceptance evidence and rollback artifact |
|---|---|---|
| 1. Reader-compatible application maintenance | High/critical advisories cleared, exact Git diff approved, hosted and real-client checks passed, deployment isolation verified and core recovery rehearsed. Keep new hash writes, cookie cutover and ordinary-role MFA off. | Smoke ordinary use and compare build ID, session/client roles and performance. Retain the last approved original and dual-reader artifact. |
| 2. Existing administrator MFA | Confirm existing enrollment support, protected schema and key custody. Verify TOTP, recovery and privileged role ceilings on synthetic deployment. | Record privileged admissions and incident access support. Roll back through a reader-compatible artifact that preserves MFA and encryption-key versions. |
| 3. Argon2id writing | Reviewed password corpus coverage, all writer families and protected SQL qualified, compatible rollback artifact, peak resource benchmark and personnel approval. | Rehearse legacy bcrypt admission, new hash verification, atomic updates and session revocation. Retain dual readers under the old and new write configuration. |
| 4. Browser cookie cutover | Confirm the web, mobile and Electron matrix, cookie domain and SameSite assumptions, and rollout order across every instance. | Record approved UTC start and seven-day legacy deadline. Use a dual-cookie reader artifact and the original deadline for rollback. |
| 5. Instructor MFA pilot and enforcement | Complete cross-client password and Google challenge admission, enrollment, factor replacement, recovery and staffed accessible support. Start with a voluntary cohort and separately approve enforcement. | Record participation, successful admissions by client, helpdesk turnaround and revoke-after-change checks. Retain the enforced privileged policy and a qualified ordinary-role pause artifact. |
| 6. Student MFA enrollment and transition | Verify multi-client challenge completion, accessibility and recovery for student cohorts. Start with optional enrollment and set explicit criteria for widening. | Demonstrate credential and academic continuity, revocation and recovery. Preserve enrolled factors and allow an approved pause in ordinary-role expansion. |
| 7. Restricted database privileges | Approve isolated Neon target and verify direct/pooled principals, role/grant SQL, scheduled jobs and backup completeness. | Compare effective grants per principal and ordinary workflows. Retain exact reviewed grant reversal sequence and prechange snapshot metadata. |
| 8. Phased RLS | Apply only after runtime grants, contextual Prisma transactions, jobs and backup verification pass. Start with an explicitly scoped Course policy in synthetic staging. | Observe role and field behavior, rollback and replay policy ownership. Retain independently reviewed forward/reverse migrations and the same prechange recovery point. |
| 9. Native distribution | Qualify signed builds, physical Android/iOS and desktop clients, trusted origin, SDK 58 update channel and signing custody. | Record signed artifact hashes, physical device acceptance and staged rollout. Keep a signed prior build and runtime-compatible updates. |
| 10. Backup and monitoring activation | Confirm actual backup, redaction, alerting and key-custody configuration under separate operational approval. Baseline recovery and alert ownership precede every production change. | Restore rehearsed archive at a single approved recovery point and verify alerts reach named responders. Record schedule, backup retention, RPO/RTO receipts and affected channels. |

**Maintenance-update option.** A smaller reader-compatible candidate can carry verified authorization, session, logging and compatible dependency fixes before advanced identity and RLS activation. Prepare a separate diff and run the same dependency, CI, real-client and recovery gates. The current high Effect advisory blocks even that maintenance path until resolved.
