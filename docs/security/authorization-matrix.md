# Server authorization matrix

The LMS backend is the Next.js application. Browser, mobile and desktop capabilities depend on server admission and the operation's policy. The middleware cookie check and UI menu visibility help routing and navigation. Authorization belongs in the handler/service and the final data access. `canonicalRole` maps `PROFESSOR`, `TEACHER` and `INSTRUCTOR` to Instructor. An unrecognized role has no grant. [Role definitions](../../apps/web/src/lib/super-user-v1/capabilities.ts) · [Roadmap](../../SECURITY-ROADMAP.md)

| Role | Course and grading | Account and institution | Explicit boundary |
|---|---|---|---|
| Student | Read approved enrolled courses. Submit and see own work and grades as allowed by the feature. Server computes grades under the existing rules. | Manage own permissible profile/session fields and use authorized activation and recovery paths. | Enrollment does not grant access to teaching operations, other students' submissions or institute database tools. |
| Instructor | Teach assigned courses in own institute. Manage classwork, give grades and export course gradebook through authorized operations. | Access roster information needed for assigned courses. Use own profile and credential operations. | Course ownership is evaluated independently of instructor role. No institute administrator account, credential or raw database capability. Program-head assignments have separate resource grants. |
| Administrator | Manage authorized courses in own institute, including gradebook export. Existing course and academic services apply operation-specific checks. | Manage eligible students/instructors in own supported institute via allowlisted fields or dedicated lifecycle operations. Export approved institute database models and update allowed existing fields through the dedicated restore workflow. MFA is required. | Cannot manage self/peer Administrator or Super User through legacy account management, transfer institute authority, access authentication vaults through raw database tools, or create rows through database restore. |
| Super User | Dedicated Super User capabilities govern its operations. Generic course, gradebook and institute admin routes exclude this role. | Dedicated, MFA-gated institute administrator lifecycle actions constrained by capability, institute selection, actor proof and protected database functions. | No inherited legacy Admin/Instructor/Student grants, ordinary student session paths, unrestricted institute data access or implicit academic controls. |

Use five separate decisions for each operation:

Sprint 4 applies those decisions to session management. Existing legacy-eligible users can revoke their own sessions. Sign-out from all devices additionally requires a fresh session. A transaction rechecks session identity and expiration and scopes deletion to the resolved actor. Only the approved session ID can be removed by a single-session request. The Super User ceiling continues to apply. The disposable RLS pilot adds proposed database read isolation and keeps the existing application course and role rules authoritative. [Sessions](session-security.md) · [RLS pilot](postgresql-rls-implementation.md)

1. **Authentication.** Resolve the same request's server session and enforce active account, provisioning and factor rules. A route guard and its service must use the same request context. Session IDs and client-submitted role or institute fields convey no authority.
2. **Role/capability.** List the roles admitted to the operation and apply the role's ceiling before exposing resource data. Keep Super User entry points separate from legacy features. Resolve a capability independently of display role labels.
3. **Resource.** Resolve the persisted target, approved enrollment or assigned instructor and verify every independently supplied resource. Apply ownership checks at the service that can actually read or write it. Mutating services should revalidate actor and target inside the appropriate existing transaction and locks.
4. **Field.** Select the required response fields explicitly. Validate permitted writes by operation and role. Identity, credentials, institution, roles and grading authority have dedicated rules. Raw database models and writable fields use the existing separate allowlists.
5. **Institute.** Derive tenant identity from the admitted account and persisted resource relationships. Bind the final Prisma predicate to that identity as well as the resource ID. A matching course ID alone does not scope student fields if stored relationships are inconsistent.

## Sprint 3 operation evidence

| Entry point | Implementation | Verification boundary |
|---|---|---|
| `GET /api/admin/users/[userId]` | Resolve the admitted session from the request, require a supported institute Administrator, and check the existing subordinate hierarchy. The final read binds ID, institute and eligible student/instructor roles. It selects only the existing profile fields, sends a private no-store response and normalizes unexpected backend errors. PATCH/DELETE and credential mutation policies remain governed by existing services. | New route tests exercise role ceiling, hierarchy, institute scope, projection and the final predicate with synthetic session and DB adapters. These cover account profile reading. |
| `GET /api/courses/[courseId]/gradebook/export` | Use the same request in the legacy guard and exporter. The exporter admits same-institute Administrators or assigned Instructors via the existing role normalizer and relationship checks. Private roster and submission queries include persisted student institute. The route returns authorization statuses and a generic unexpected failure. | New role, relationship, query and response tests use synthetic records. The existing CSV grading fixture checks period, pending and zero-score behavior. The dashboard action uses the same exporter and retains its separate `executeSkill` result contract. |
