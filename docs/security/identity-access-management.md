# Identity and access management proposal

This proposal covers AUTH-01/02/05/06/07/08. The existing administrator and Super User MFA requirement stays in force. Identity policy and runtime changes below require owner approval. Sprint 3 changed the use of the existing session actor in two authorization operations. [Authorization matrix](authorization-matrix.md) · [Administrator MFA rollout](admin-mfa-production-rollout.md)

## AUTH-02 password and hashing migration

Current new-password rules are implemented in `apps/web/src/lib/auth-schema.ts`. They use character composition and a 72-byte bound aligned with bcrypt. Keep legacy verification behavior for existing hashes. Target a minimum of 15 Unicode code points for newly set passwords, allow at least 64, and propose a maximum of 128 code points with a 512-byte UTF-8 cap before hashing. Permit spaces, Unicode, paste, autofill, reveal controls and password managers. Agree a consistent NFC normalization rule only for newly stored Argon2id credentials. Reject common, context-specific and compromised choices on set/change. Start with a versioned local blocklist so the LMS can check choices without transmitting them to a third party. Refresh on a documented schedule and return meaningful replacement guidance. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

1. Inventory every password reader and writer before deployment. Include login, account setup, roster activation, account changes, administrator provisioning, reset, operator SQL guards, desktop/mobile compatibility and any remaining fallback paths. Verify column capacity and credential-revocation triggers. Add Argon2id read support everywhere before enabling writes.
2. Use a reviewed Node-runtime library and PHC-format storage. Benchmark memory, CPU and latency under cold starts and concurrent login bursts. Start the benchmark at OWASP's 19 MiB, two iterations and parallelism one. Choose production cost from measured p95 and memory headroom. Bound KDF concurrency and request size, apply distributed limits before costly work, and keep serverless resource exhaustion from turning into mass denial. [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
3. Write Argon2id for new credentials and changes after dual verification is deployed everywhere. Consider conditional rehash after successful full admission using compare-and-swap on the previous hash. Bcrypt's 72-byte equivalence cannot safely identify the original long password. For ambiguous inputs use an explicit credential change rather than silently choosing a different full password. Privileged MFA currently binds proof to the password hash and database triggers react to credential changes. Keep privileged opportunistic rehash disabled until a reviewed transaction can preserve factor assurance and revoke or reissue sessions coherently.
4. Gate writes separately from reads. Rollback stops new writes while retaining Argon2id read support and both sets of hashes. A bcrypt-only rollback would strand migrated users. Record migration totals by scheme with no hashes or passwords in telemetry. Retire legacy writes once all application and operator paths support the new scheme.

## AUTH-05 staged MFA and recovery

Use passkeys/WebAuthn as a phishing-resistant option, existing TOTP concepts as an accessible alternative where appropriate, and single-use recovery codes independent of the authenticator. Provide desktop/browser setup, manual code entry in addition to QR, labelled fields, paste, screen-reader instructions, keyboard support and a supervised fallback for users without a personal device. Pilot with volunteer instructors and accessibility users before enforcement. Budget time for enrollment reminders, device replacement, clock skew, platform/browser coverage and staffed recovery. Measure successful enrollment and recovery without exposing factor data. Avoid email-only factor reset for privileged roles. Account and factor recovery revoke prior sessions, generate a metadata-only event and notify via a verified channel. Owner must agree coverage thresholds, recovery evidence, administrator oversight and pilot rollback. Pausing an instructor enrollment deadline never disables administrator MFA.

## AUTH-06/07 sessions, browser and native

`auth-session.ts` and `session-policy.ts` use opaque random tokens with DB hashes, seven-day absolute and 30-minute idle limits and passive-request handling. Logout removes server state. Privileged MFA is checked on admission. Browser `lumina_session` is HttpOnly, Secure in production, SameSite=Lax and Path `/`. The challenge cookie has a separate path and strict SameSite policy. Native requests keep the existing bearer shape. Mobile storage and authentication validation previously blocked in run2 remain excluded.

Recommend keeping server-side opaque sessions, with documented expiration budgets by role and fresh factor confirmation for factor management and similarly sensitive actions. Rotate at login and assurance/privilege changes, bind replacement to the authenticated identity and revoke obsolete state transactionally. Define logout-current and revoke-all behavior for deactivation, credentials, factor reset and compromise. Keep passive requests from extending expiry. Benchmark session lookup/touch traffic and support older clients during the transition.

Consider a production `__Host-` cookie after a compatibility inventory. It requires Secure, Path `/` and omission of Domain. Preserve callback and desktop browser behavior with a bounded dual-read transition, one canonical writer, deterministic precedence, explicit old-cookie removal and matching middleware, API and logout updates. Keep MFA challenge path semantics separate. Plan offline synthetic web/mobile/desktop contract checks, then owner-controlled signed device checks according to the relevant MASVS domains. [OWASP MASVS](https://mas.owasp.org/MASVS/)

## AUTH-08 distributed rate limiting

Password login and selected roster/MFA paths already use persisted counters. General request limiting has an in-memory implementation. Recommend extending the existing atomic PostgreSQL `RateLimitBucket` pattern before introducing another service. Document per-operation, per-account and per-client limits, uniform responses and `Retry-After` where safe. Derive pseudonymous keys from canonical identities with a separately managed keyed digest where linkability is sensitive. Define expiry cleanup, storage cardinality limits, contention alerts and bounded pool timeouts. Calculate database cost under multiple instances and hot keys. Keep security-sensitive issue/verify routes fail-closed on store failure with a retryable unavailable response. Measure legitimate NAT/shared-lab traffic and recovery abuse risk before setting limits. Keep the client-address chain an operator prerequisite and obtain ingress configuration evidence before trusting a proxy header. No change to ingress trust or provider is authorized by this proposal.

Roll out in this order after approval: inventory and dual verifier, limited Argon2id writes and monitoring, instructor MFA pilot, then cookie/session/limiter changes in separately reversible batches. Owner to approve password limits and blocklist cadence, factor and recovery policy, session duration and migration, and database counter retention/failure behavior. Publish an operator sign-off and tested rollback for each batch.
