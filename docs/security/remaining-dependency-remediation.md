## Approval proposal for the mobile high advisory

**Recommended. Approve a separate SDK 57 → 58 migration branch.** Start with Expo 58.0.26 and select its supported Router 58 patch and peer set. Registry evidence identifies Router 58.0.32 as a candidate. Expo SDK 58 moves React Native 0.86 to 0.88 and updates the iOS and Android native toolchain. Align React, Metro, Constants, Linking, Screens, Reanimated/Worklets, Expo config plugins and native dependencies via the SDK compatibility set. Preserve the existing scheme, bundle IDs, Android application ID, API origins, notification routes, Google callback and published client/server compatibility. [Expo SDK 58 release notes](https://expo.dev/changelog/sdk-58) · [Official upgrade workflow](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/)

The integrity-checked Expo 58.0.26 distribution lists React 19.3.0, React Native 0.88.1, Router `~58.0.32`, Screens `~4.30.1`, Gesture Handler `~3.3.0`, Reanimated 4.7.1, Worklets 0.13.0, WebView 14.0.1 and Sentry `~8.28.0`. The migration therefore affects native gesture, animation, embedded content and error reporting in addition to routing. Check TypeScript changes, iOS scene-based cold/warm link delivery, Android release shrinking, notification handling and Expo environment loading. The mobile project currently leaves web output implicit. Preserve its existing hosted backend and explicitly review web output during migration so the new Router default cannot silently introduce a second backend. Use Node 22.23.3 with a clean synthetic environment for local verification. [Published Expo package](https://registry.npmjs.org/expo/58.0.26) · [SDK 58 breaking changes](https://expo.dev/changelog/sdk-58#notable-breaking-changes)

1. Freeze the SDK 57 source, lock, Expo configuration and known artifact IDs. Record route manifests, notification destinations and deep-link contracts. Build the SDK 58 candidate on a separate branch and inspect regenerated native configuration before accepting it.
2. Confirm the complete dependency graph removes the decoder path and introduces no new high or critical advisory. Run explicit mobile compatibility and web API contract tests, mobile typecheck, Expo Doctor, Android/iOS bundles and native builds in approved environments.
3. On owner-controlled staging devices, check cold/warm navigation, back behavior, Google sign-in and cancellation, session resume, course views/grades, CodeLab, assessments, attendance and notification routing during ordinary use. Preserve the blocked security-validation scope. Device recovery and distribution checks remain explicit release evidence.
4. Use a fresh runtime version/channel for incompatible native JS updates. Keep the signed SDK 57 build and matching source/lock/config to address a functional rollback, subject to the unresolved advisory and explicit owner risk acceptance. If a failure is discovered after rollout, halt promotion and use the platform-supported signed rollback or forward fix. Never deliver SDK 58 JavaScript to the SDK 57 binary. No production rollout is part of this proposal.

**Alternative. Request a supported SDK 57 backport** of the router query-parameter change and monitor stable releases. This minimizes native churn but has no confirmed delivery date. A downstream SDK 57 backport could be evaluated with separate maintenance and compatibility approval. Forcing a decoder or query-string major beneath Router 57 would bypass the published contract and risks ESM and parsing differences. Replacing Expo Router with a maintained navigation library would require reimplementing file routes, typed links, tabs, deep links and notification destinations. That has a larger migration and rollback cost than the supported SDK upgrade.

Owner decision requested on the SDK 58 migration. Existing legitimate routing and tunnel functionality remain available. The dependency gate continues to fail while the high match remains.
