# Administrator authenticator MFA

Administrator and Super User sign-in requires a password plus an authenticator app or one unused recovery code. This is separate from the legacy password-change PIN. The existing Google web/mobile flows remain student-only; they do not grant an administrator session.

## Rollout

This source change does not enroll real devices, apply production migrations or configure hosting secrets. Prepare these steps together before deployment:

1. Apply `prisma/migrations/20261115010000_admin_mfa/migration.sql` using the reviewed migration principal. Grant the existing restricted runtime principal only the required CRUD on the three new MFA tables, following the deployment's established grant policy. Do not grant PUBLIC access or make the runtime principal an owner/superuser.
2. Regenerate Prisma from the current schema and restart application workers so they use the same schema/client version.
3. Set the server-only `ADMIN_MFA_ENCRYPTION_KEY` to canonical Base64 encoding of 32 cryptographically random bytes. Store it in protected hosting secrets; never use `NEXT_PUBLIC_`, commit it, share it with students, or reuse a provider/API credential. Keep a protected recovery copy. Without the correct key, new authenticator verification is unavailable; key rotation requires a separately reviewed re-encryption/reset procedure.
4. Deploy the tested candidate and have each real administrator sign in, scan the locally generated QR or enter the setup key, verify a current code, save the ten recovery codes privately, and acknowledge that they have saved them. A password-only or historical privileged session will no longer authorize administrator requests. Students and instructors retain their existing session flow.

Apply and verify the schema/key before exposing the new application candidate. Missing MFA configuration/schema fails closed for administrator admission. The new models add relations rather than new scalar columns to User/Session, so non-admin session reads do not depend on querying the new tables.

## Enrollment and sign-in

Password verification creates only a ten-minute opaque HttpOnly, SameSite=Strict cookie scoped to `/api/auth/mfa`. It does not insert an administrator Session. `/mfa` uses that challenge to show enrollment or verification. Secrets and QR images are generated by the LMS and returned only to the primary-authenticated browser with no-store headers; no third-party QR service receives them.

Successful second-factor verification rotates the challenge token. Its verified proof is valid for at most two minutes and is consumed once inside the same transaction that creates a separate random Session token. Enrollment additionally requires explicit recovery-code acknowledgment before the factor or Session is created. Reloading the enrollment page cannot retrieve already displayed recovery codes; restart password sign-in if they were lost before acknowledgment.

TOTP uses RFC 6238 SHA1, six digits, a 30-second period and a one-step clock tolerance. A monotonic counter under account/factor locks rejects sequential and concurrent replay. Recovery codes contain 128 random bits each, are stored only as user-bound hashes and are atomically removed when used. They are displayed only during initial enrollment; there is no password-only factor removal or recovery reset endpoint.

The opaque challenge is bound to the current email, password hash, role, institute, Google subject, credential lifecycle and browser user-agent. Expiry, account deactivation and changed credentials/authority invalidate it. Database triggers also revoke pending challenges, proofs and privileged sessions on critical account transitions, including edit/revert and suspend/reactivate cycles. Factor deletion or a change of factor owner, secret or epoch revokes sessions and challenges atomically. Session proofs are bound to the same credential identity and a random factor epoch; never restore an old epoch. Central session validation and privileged transaction revalidation enforce the proof, including refresh and sibling APIs. Administrative revoke-all operations cancel pending sign-ins even when there are zero existing sessions, under the same institute and hierarchy restrictions.

Native API clients receive a clear instruction to finish administrator authentication in the secure web portal; they never treat a pending MFA response as a usable token. Student/faculty mobile sign-in is unchanged. Desktop users use the same web MFA page.

## Operational limits

Real administrator enrollment remains a human action. The agent must not manufacture authenticator enrollment or choose an administrator's device. Lost-device recovery uses an unused recovery code plus the password; if both the authenticator and all codes are lost, an authorized operator must verify identity through the institution's process before a reviewed factor reset. Preserve the MFA audit log and revoke sessions/challenges during that reset. No public password-only recovery flow resets administrator MFA.

Authentication logs contain event names, never TOTP secrets, codes, challenge tokens or recovery values. `ADMIN_MFA_ENROLLED`, `ADMIN_MFA_VERIFIED` and `ADMIN_MFA_RECOVERY_USED` are recorded without secret metadata. Online guessing is bounded by persistent IP and account limits, and database lock/statement/transaction deadlines are explicit.

## Permanent regression checks

`tests/security/admin-mfa.test.cjs` covers RFC vectors, replay windows, authenticated encryption/AAD, recovery-code hashing, credential identity bindings, Google web/mobile administrator rejection, and native pending-login handling. `tests/security/admin-mfa-cases.cjs` runs last in the disposable current-schema PostgreSQL fixture and checks no Session before MFA, legacy-session denial, acknowledgment, token rotation/consumption, concurrent TOTP/recovery replay, cancellation, expiry, user-agent binding and factor-reset invalidation.

These tests use synthetic accounts, secrets and a disposable database. Passing them does not establish that production migration/key provisioning or any real device enrollment has happened.
